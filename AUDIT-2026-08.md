# PinPlay — Audit Mendalam (2026-08-06)

Cakupan: 65 file `src/`, plus `launcher.js`, `scripts/`, `data/*.json`.
Metode: 4 auditor paralel per subsistem, temuan severity tinggi diverifikasi ulang manual + dieksekusi di Node.

Ringkasan: **4 CRITICAL, 8 HIGH, 13 MEDIUM.** Tiga bug paling serius sudah dikonfirmasi dengan eksekusi kode, bukan sekadar pembacaan.

## CRITICAL

### C1 — `/djrole set` tanpa permission check: siapa pun bisa jadi DJ

`src/commands/djrole.js:3` mengimpor `isAdmin`, **tidak pernah memanggilnya**. `djrole.js:32-33`:

```js
const role = interaction.options.getRole("role", true);
setGuildSettings(interaction.guildId, { djRoleId: role.id });
```

`permissions.js:27` mempercayai `djRoleId` penuh di mode restricted:

```js
if (settings.djRoleId && roles?.has(settings.djRoleId)) return true;
```

**Dampak:** member biasa jalankan `.dj set @RoleYangDiaPunya`, langsung dapat kontrol penuh — `stop`, `leave`, `clear`, `skip`, `volume`, `filter`, semua tombol panel. Mode restricted bobol dengan satu command, persisten, tanpa jejak audit. Semua command lain sudah bergerbang benar (`247.js:28`, `access.js:83`, `panel.js:25`) — hanya command yang *mengatur* gerbang yang bolong.

**Fix:** tambah di awal `execute`, sebelum cabang `view`:

```js
if (!isAdmin(interaction)) {
  return interaction.reply({ embeds: [errorEmbed("❌ Command ini khusus Administrator.")], flags: 64 });
}
```

### C2 — Tidak ada error boundary: satu unhandled rejection mematikan bot

Grep `process.on` di seluruh `src/` → **nol hasil** (hanya ada di `launcher.js`, proses berbeda). Node ≥18 default `--unhandled-rejections=throw`.

`src/index.js:102` — `client.login(config.discord.token);` tanpa `.catch()`.

Jalur reject yang nyata dan sudah teridentifikasi:
- `interactionHandler.js:104` — `player.play()` tanpa `await`, lolos dari `try` sekitarnya.
- `messageHandler.js:36` — `return handleChatReply(...)` tanpa `await`, lolos dari `try/catch` di `:81-98`. Ini jalur panggilan AI — paling sering gagal (5xx provider).

**Dampak:** bot mati total tanpa log penyebab, tanpa restart. Tidak ada `client.destroy()` saat SIGTERM.

**Fix** (~8 baris di `index.js`):

```js
process.on("unhandledRejection", (e) => log.error("unhandledRejection:", e));
process.on("uncaughtException", (e) => { log.error("uncaughtException:", e); process.exit(1); });
for (const sig of ["SIGINT", "SIGTERM"]) {
  process.on(sig, () => { flushNow(); client.destroy(); process.exit(0); });
}
client.login(config.discord.token).catch((e) => { log.error("Login failed:", e?.message || e); process.exit(1); });
```

### C3 — `guildSettings.json` bisa hancur total, dan gagalnya fail-open

Dua cacat bertumpuk di `src/utils/storage.js`.

**Non-atomic write** — `storage.js:43`:
```js
fs.writeFileSync(settingsFile, JSON.stringify(_cache, null, 2), "utf-8");
```
`writeFileSync` truncate dulu baru tulis. Crash di tengah → file kosong/separuh → **semua guild hilang sekaligus**.

**Fail-open saat korup** — `storage.js:26-30`:
```js
try { _cache = JSON.parse(raw); } catch { _cache = {}; }
```
Diam-diam reset ke `{}`. Setiap guild balik ke `controlMode: "all"` — akses kontrol **gagal ke arah terbuka**, tanpa satu baris log.

**Tanpa flush saat exit** — `_scheduleSave` debounce 500 ms, dan setiap perubahan cepat memanggil `clearTimeout` yang *mengundur* deadline lagi. Ctrl-C atau SIGTERM di dalam window → tulisan hilang.

Ironisnya helper yang benar sudah ada di repo ini: `jsonFile.js:8-10` (`atomicWriteJsonSync`, temp+rename) dan dipakai subsistem AI. `storage.js` — yang memegang `controlMode` dan `djRoleId` — justru tidak memakainya.

**Fix:** ganti baris 43 ke `atomicWriteJsonSync(settingsFile, _cache)`, ekspor `flushNow()`, panggil dari handler SIGINT/SIGTERM di C2, dan log saat catch korupsi.

> C1 + C3 saling memperkuat: C3 mereset `controlMode` ke `"all"`, C1 membiarkan siapa pun merebut DJ. Akses kontrol gagal terbuka dari dua arah.

### C4 — Token usage tracking mati diam-diam sejak 14 bulan lalu

`src/utils/ai.js:293` memakai `opts.model`, tapi parameter didestrukturisasi di `:262` — **`opts` tidak pernah terikat**.

Dibuktikan dengan eksekusi:
```
THROWS: ReferenceError: opts is not defined
```

Throw itu tertangkap `catch` di `:298` yang isinya `log.debug(...)` — dan `LOG_LEVEL` default `info`, jadi **tidak pernah tercetak sama sekali**.

`git log -S'opts.model'` → commit `43c7504`, 2026-06-17. `data/aiTokenUsage.json` `lastUpdated` = **2026-06-17**. Pencatatan berhenti persis di hari itu.

Data yang tersisa juga korup: nvidia tercatat 1.000.150 token dalam **2 panggilan** = 500.075 token/panggilan, mustahil untuk context window 70B. Jadi `/ai-set tokens stats` dan `getEstimatedCost()` melaporkan fiksi — padahal itu satu-satunya kontrol biaya yang dimiliki owner.

**Fix:** satu kata — `model: model || resolvedModel`. Perbaiki ini duluan, karena C4 yang membutakan Anda terhadap H3.

## HIGH

### H1 — Output AI bisa nge-ping `@everyone`

Seluruh `src/` hanya punya **satu** `allowedMentions`, di `events.js:135`. Empat `followUp` di `roast.js` (`:116`, `:141`, `:167`, `:210`) mengirim **string telanjang**:

```js
await interaction.followUp(text.slice(0, 1950));
```

String → tanpa `allowedMentions` → mention di-resolve. Prompt roast dirancang agresif, `temperature: 0.9` (varians tertinggi di codebase), dan judul lagu yang dikontrol user masuk langsung ke prompt. User bisa menamai track `@everyone lol` untuk menyetir output.

`/chat` selamat *kebetulan* karena membungkus output di embed description — invariant rapuh, bukan penjagaan.

**Fix:** di empat situs itu, plus satu baris global di `index.js` ClientOptions:
```js
allowedMentions: { parse: [], repliedUser: true },
```
Baris global itu juga menutup `messageHandler.js:74` yang meng-echo pesan error berisi input user (`.v @everyone` → bot mengetik `@everyone`).

### H2 — Autoplay: cabang Spotify seluruhnya dead code

`autoplay.js:47` mengecek `typeof spotifyModule.getRecommendations === 'function'`. Grep `spotify.js:596` — daftar ekspor **tidak memuat `getRecommendations`**. Selalu `false`.

Konsekuensi: blok `autoplay.js:140-154` membakar satu `Promise.race` + timer 5 detik setiap autoplay pada track Spotify, lalu selalu jatuh ke YouTube. Andai fungsinya ada, `recs[0]` adalah objek rekomendasi Spotify mentah — bukan `KazagumoTrack`, tanpa field `encoded`, tidak bisa diputar Lavalink.

**Fix termurah:** hapus `fetchFromSpotify` (`:33-60`) dan cabangnya (`:140-154`). Modul jadi lebih pendek *dan* lebih benar.

### H3 — Biaya `/chat` membengkak kuadratik

`chat.js:53` membatasi 40 *pesan*, tidak pernah *token*. Tiap giliran assistant di-generate dengan `maxTokens: 1024`, jadi window penuh ≈ **41k token riwayat dikirim ulang setiap panggilan**, plus system prompt (kartu personality 300-500 token) plus memory.

Balasan ke-20 berbiaya ~20× balasan pertama, sementara user merasa "satu pesan = satu request". TTL 10 menit bisa dijaga hidup terus-menerus dengan membalas.

Konsisten dengan data: `bySource.chat` = 1.013.652 token / 20 panggilan ≈ **50k token per panggilan**.

**Fix:** batasi berdasarkan karakter (proksi token yang memadai, tanpa tokenizer):
```js
const MAX_HISTORY_CHARS = 12_000;
let chars = session.messages.reduce((n, m) => n + m.content.length, 0);
while (chars > MAX_HISTORY_CHARS && session.messages.length > 2) {
  const [a, b] = session.messages.splice(0, 2);
  chars -= a.content.length + b.content.length;
}
```
Ini penghematan tunggal terbesar di seluruh codebase.

### H4 — Fallback menggandakan biaya saat kena rate limit

`aiProviderFallback.js:139-146` — header modul menyatakan 429 dan 401 "NOT retried", tapi kode `break` lalu **tetap jatuh ke fallback**. Kena 429 (kuota habis) atau 401 (key salah) di provider utama langsung mengirim ulang seluruh prompt (yang sudah membengkak karena H3) ke provider satunya. Worst case 3 panggilan penuh per satu request user.

**Fix:** `if (st === 401 || st === 403 || st === 429) throw err;` — error yang tidak bisa diperbaiki provider lain jangan di-fallback. Perlu juga menyimpan `e.status` saat rethrow di `ai.js:314-331`, karena di sana status hilang saat diterjemahkan ke pesan Indonesia.

### H5 — Tombol Prev macet di satu lagu

`panelInteractions.js:184` — `player.getPrevious()` dipanggil tanpa argumen. Dokumentasi Kazagumo: `getPrevious(remove?)`, "Best to set to true if you want to play it." Tanpa `true`, track tidak dikeluarkan dari daftar previous — tekan Prev dua kali menghasilkan lagu yang sama, selamanya.

**Fix:** `player.getPrevious(true)`.

### H6 — Dua instance RateLimiter: kuota efektif dobel

`interactionHandler.js:13` dan `messageHandler.js:19` masing-masing `new RateLimiter()`. Komentar di `messageHandler.js:18` menulis "Reuse rate limiter dari interaction handler" — **salah**, ini instance kedua dengan Map terpisah.

User dapat 3 hit slash **dan** 3 hit prefix per 5 detik, dan bisa selang-seling (`/skip`, `.s`, `/skip`, `.s`) untuk menahan 6/5s ke handler mahal termasuk AI.

**Fix:** ekspor singleton `shared` dari `rateLimiter.js`, pakai di kedua handler.

### H7 — Rate limiter menghitung setiap klik tombol panel

`interactionHandler.js:20` memanggil `rateLimiter.check()` di **paling atas**, sebelum membedakan jenis interaction. `rateLimiter.js:26` melakukan `user.hits += 1` di setiap panggilan. Dengan `maxHits=3 / 5s`, user yang menekan tombol panel 4 kali dalam 5 detik kena throttle. Panel adalah UI utama — ini membuat pemakaian normal terasa rusak.

**Fix:** pindahkan cek rate limit ke bawah, setelah cabang button/modal/select, hanya untuk `isChatInputCommand()`.

### H8 — Timer auto-leave bisa menghancurkan sesi yang sedang dimuat

`events.js:34-53` — closure menangkap objek `player`. Timer dibersihkan pada `playerStart` dan `playerDestroy`, tapi **tidak** saat track ditambahkan ke player idle.

Skenario nyata: playlist Spotify besar sedang di-resolve (`spotify.js:283-331` tidur 750 ms per 2 track). Jika resolusi track pertama lebih lama dari sisa timeout, timer menyala saat `queue.size === 0 && !playing` masih benar → player dihancurkan di tengah pemuatan → sisa playlist dibatalkan.

**Fix:** panggil `clearLeaveTimer` tepat setelah `queue.add` di jalur play, atau perketat kondisi timer dengan `&& !player.queue.current`.

## Yang sudah benar (jangan "diperbaiki")

- `searchCache.js` — TTL + LRU bound + move-to-end. Bersih.
- `aiLimits.js` — counter di-increment **sebelum** panggilan API (arah yang aman), fully synchronous jadi tidak ada race, dan mengirim `__test_concurrent__` sebagai self-check. Bagian paling rapi di codebase.
- Token cache Spotify — margin 60 detik, benar di tiga situs.
- `AbortSignal.timeout` ada di semua fetch scraping Spotify. Hanya lrclib yang bolong.
- Owner check & whitelist `/chat` — tidak ada bypass; jalur prefix dan slash memakai `execute` yang sama.
- Autoplay memicu di `playerEnd`, bukan `playerStart` — alasan di komentar `events.js:138-145` benar.
- `history.js` bounded 20, menyimpan objek datar bukan `KazagumoTrack` penuh.
- Setiap command playback mutating **sudah** bergerbang `requireControl` — kecuali `/djrole` (C1).

## Saran upgrade & fitur

**Ringankan:**
1. Debounce `updatePanel` per guild (~2 detik). Playlist 100 track: 50 edit → ~3. Satu Map + satu timer.
2. `makeCache` + `sweepers` (M1). Penghematan memori terbesar, 6 baris.
3. Ganti classifier personality dengan keyword match lokal, fallback ke AI saat miss. Menghapus satu round-trip dan hingga 90 detik latensi per sesi baru.

**Kurangi duplikasi:** 14 file command mengulang preamble 6 baris yang identik (`getPlayer` + `getGuildSettings` + `requireControl`) ≈ 140 baris. Satu wrapper `withControl(fn)` menghapusnya *dan* membuat gerbang izin jadi satu lokasi yang bisa diaudit — sehingga "apakah command ini sudah bergerbang?" berhenti jadi grep 23 file. Persis kelas bug C1.

**Fitur:** `/autoplay` akan terasa jauh lebih baik setelah dedup history (M4). Sisanya, saya sarankan tidak menambah fitur sampai C1-C4 beres.
